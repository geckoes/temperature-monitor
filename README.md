# Temperature Monitor

![CI](https://github.com/geckoes/temperature-monitor/actions/workflows/ci.yml/badge.svg)

A production-oriented backend service for collecting, storing, and querying temperature measurements produced by external sensors.

The project is built with **Java and Spring Boot** and is being developed incrementally using a **TDD-oriented workflow**, with particular attention to REST API design, persistence, testability, time-series data, and separation of responsibilities.

## Why This Project?

Temperature Monitor is more than a CRUD example.

Its goal is to explore engineering decisions commonly found in backend and distributed systems, including:

- designing stable REST API boundaries;
- separating API contracts from persistence models;
- handling event timestamps independently from ingestion timestamps;
- querying time-series data;
- validating API requests and combinations of query parameters;
- managing database schema evolution;
- testing application layers independently;
- keeping deployment-specific configuration outside the source code.

The project will progressively evolve toward simulated external sensors, observability, resilience, and asynchronous data ingestion.

---

## Current Features

- Receive temperature measurements through a REST API
- Persist historical measurements in PostgreSQL
- Support Celsius and Fahrenheit units
- Associate measurements with logical sensor identifiers
- Preserve sensor-generated timestamps (`measuredAt`)
- Record server-side ingestion timestamps separately (`createdAt`)
- Query all measurements
- Filter measurements by sensor
- Filter measurements by sensor and time range
- Validate incoming measurement requests
- Validate combinations of query parameters
- Keep REST request/response DTOs separate from JPA entities
- Manage database schema changes with Flyway

## Architecture

The application currently follows a layered architecture:

```text id="r26shv"
External Sensor / Client
          |
          | HTTP / JSON
          v
    REST Controller
          |
          v
       Service
          |
          v
      Repository
          |
          | JPA / Hibernate
          v
      PostgreSQL
```

The REST API does not expose JPA entities directly.

Instead, dedicated DTOs define the external contract:

```text id="7krlhy"
JSON
  |
  v
TemperatureMeasurementRequest
  |
  v
Service / Domain
  |
  v
TemperatureMeasurement
  |
  v
TemperatureMeasurementResponse
  |
  v
JSON
```

This keeps the API contract decoupled from the persistence model and allows both to evolve independently.

## Measurement Model

A measurement received from a sensor contains:

- `temperature`
- `unit`
- `sensorId`
- `measuredAt`

The system additionally maintains:

- an internal database identifier;
- `createdAt`, representing when the server persisted the measurement.

### Event Time vs Ingestion Time

`measuredAt` and `createdAt` intentionally represent different concepts.

For example:

```text id="urw5go"
10:00:00  Sensor measures 23.5 °C
10:00:01  Network connection becomes unavailable
10:04:00  Connection is restored
10:04:01  Measurement reaches Temperature Monitor
```

The measurement still represents the temperature at `10:00:00`, not `10:04:01`.

Therefore:

```text id="2zntq8"
measuredAt -> event time generated by the sensor
createdAt  -> ingestion/persistence time generated by the server
```

This distinction becomes important when dealing with delayed events, retries, offline sensors, and distributed systems.

# REST API

## Create a Measurement

```http id="e2z9se"
POST /api/measurements
Content-Type: application/json
```

Example request:

```json id="u48wz2"
{
  "temperature": 23.5,
  "unit": "CELSIUS",
  "sensorId": "sensor-001",
  "measuredAt": "2026-09-07T10:00:00Z"
}
```

Example response:

```json id="c3hkgc"
{
  "id": 1,
  "temperature": 23.5,
  "unit": "CELSIUS",
  "sensorId": "sensor-001",
  "measuredAt": "2026-09-07T10:00:00Z"
}
```

Persistence-specific fields such as `createdAt` are deliberately not exposed by the current API contract.

---

## Get All Measurements

```http id="73vvkt"
GET /api/measurements
```

---

## Filter by Sensor

```http id="1j7l2m"
GET /api/measurements?sensorId=sensor-001
```

---

## Filter by Sensor and Time Range

```http id="1rm8g5"
GET /api/measurements?sensorId=sensor-001&from=2026-09-07T10:00:00Z&to=2026-09-07T12:00:00Z
```

A time range currently requires:

- `sensorId`
- `from`
- `to`

Incomplete or invalid combinations result in `400 Bad Request`.

# Testing Strategy

The project is developed incrementally following a TDD-oriented cycle:

```text id="fqpd7q"
RED -> GREEN -> REFACTOR
```

The test suite deliberately separates different responsibilities.

### Service Tests

Service dependencies are mocked with Mockito.

These tests verify application behavior and interactions without accessing the real database.

### Controller Tests

Controller tests use MockMvc and mocked services to verify:

- HTTP status codes
- JSON contracts
- request validation
- query parameter handling
- service interactions

### Repository Integration Tests

Repository tests exercise the actual persistence layer and verify Spring Data JPA queries against PostgreSQL.

For example, repository integration tests verify that sensor and time-range filters return only the expected measurements.

Transactional tests are rolled back to keep tests isolated.

### Application Context Test

The application context test verifies that the Spring Boot application can start with the expected configuration.

# Configuration

Runtime-specific configuration is externalized from the application.

The default configuration supports environment variables:

```properties id="1hpm9v"
spring.datasource.url=jdbc:postgresql://${DB_HOST:localhost}:${DB_PORT:5432}/${DB_NAME:temperature}
spring.datasource.username=${DB_USERNAME:postgres}
spring.datasource.password=${DB_PASSWORD:}

server.port=${SERVER_PORT:8080}
```

Default values:

| Setting | Default |
|---|---|
| Database host | `localhost` |
| Database port | `5432` |
| Database name | `temperature` |
| Database user | `postgres` |
| HTTP port | `8080` |

Local development environments can override these values without modifying version-controlled configuration.

For example, a developer may use an untracked:

```text id="0cj0zp"
application-local.properties
```

to configure local database credentials or non-standard ports.

Secrets and machine-specific configuration must not be committed to the repository.

# Database Migrations

Database schema evolution is managed using **Flyway**.

The initial migration creates the `temperature_measurements` table together with its integrity constraints.

Flyway owns schema evolution, while Hibernate/JPA maps the application model onto that schema.

# Running Locally

## Requirements

- Java 17+
- PostgreSQL
- Maven, or the included Maven Wrapper
- Docker, if PostgreSQL is run in a container

Start PostgreSQL using your preferred local setup.

Then start Temperature Monitor:

```bash id="nv7u5p"
./mvnw spring-boot:run
```

If using a local Spring profile:

```bash id="t7n0xv"
./mvnw spring-boot:run -Dspring-boot.run.profiles=local
```

Run the complete test suite with:

```bash id="7zw6ra"
./mvnw test
```
