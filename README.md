# Temperature Monitor

![CI](https://github.com/geckoes/temperature-monitor/actions/workflows/ci.yml/badge.svg)

A production-oriented backend service for collecting, storing, and querying temperature measurements produced by external sensors.

The project is built with **Java and Spring Boot** and is being developed incrementally using a **TDD-oriented workflow**, with particular attention to REST API design, persistence, testability, time-series data, and separation of responsibilities.

---

## Why This Project?

Temperature Monitor is more than a CRUD example.

Its goal is to explore engineering decisions commonly found in backend and distributed systems, including:

- designing stable REST API boundaries;
- separating API contracts from persistence models;
- handling event timestamps independently from ingestion timestamps;
- querying time-series data;
- validating API requests and combinations of query parameters;
- managing database schema evolution;
- testing application layers independently;
- keeping deployment-specific configuration outside the source code.

The project will progressively evolve toward simulated external sensors, observability, resilience, and asynchronous data ingestion.

---

## Current Features

- Receive temperature measurements through a REST API
- Persist historical measurements in PostgreSQL
- Support Celsius and Fahrenheit units
- Register and retrieve sensors with unique logical identifiers
- Assign or replace a sensor's current terminal without rewriting measurement history
- Associate accepted measurements with registered sensors through a database foreign key
- Preserve terminal origin in measurements
- Quarantine unknown sensors, unassigned or mismatching terminals, and measurement conflicts
- Recognize identical retries and recover concurrent measurement insert conflicts
- Preserve sensor-generated timestamps (`measuredAt`)
- Record server-side ingestion timestamps separately (`createdAt`)
- Query all measurements
- Paginate measurement queries
- Support configurable and multi-field sorting
- Provide deterministic default ordering for measurement results
- Filter measurements by sensor
- Filter measurements by sensor and time range
- Validate incoming measurement requests
- Validate combinations of query parameters
- Return consistent ProblemDetail error responses for invalid requests
- Keep REST request/response DTOs separate from JPA entities
- Manage database schema changes with Flyway
- Run automated tests through CI

## Architecture

The application currently follows a layered architecture:

```text
External Sensor / Client
          |
          | HTTP / JSON
          v
    REST Controller
          |
          v
       Service
          |
          v
      Repository
          |
          | JPA / Hibernate
          v
      PostgreSQL
```

The REST API does not expose JPA entities directly.

Instead, dedicated DTOs define the external contract:

```text
JSON
 |
 v
TemperatureMeasurementRequest
 |
 v
Service / Domain
 |
 v
TemperatureMeasurement
 |
 v
TemperatureMeasurementResponse
 |
 v
JSON
```

This keeps the API contract decoupled from the persistence model and allows both to evolve independently.

## Measurement Model

A measurement received from a sensor contains:

- `temperature`
- `unit`
- `sensorId`
- `terminalId`
- `measuredAt`

The system additionally maintains:

- an internal database identifier;
- `createdAt`, representing when the server persisted the measurement.

### Event Time vs Ingestion Time

`measuredAt` and `createdAt` intentionally represent different concepts.

For example:

```text
10:00:00  Sensor measures 23.5 °C
10:00:01  Network connection becomes unavailable
10:04:00  Connection is restored
10:04:01  Measurement reaches Temperature Monitor
```

The measurement still represents the temperature at `10:00:00`, not `10:04:01`.

Therefore:

```text
measuredAt -> event time generated by the sensor
createdAt  -> ingestion/persistence time generated by the server
```

This distinction becomes important when dealing with delayed events, retries, offline sensors, and distributed systems.

# REST API

## Sensor Registry

Register a sensor before sending new measurements. The project currently models
one terminal per logical sensor, with a terminal assigned to at most one sensor.

### Register a sensor

```http
POST /api/sensors
Content-Type: application/json
```

```json
{
  "sensorId": "sensor-001",
  "terminalId": "terminal-A",
  "name": "North Warehouse"
}
```

Returns `201 Created`, a `Location: /api/sensors/sensor-001` header and:

```json
{
  "sensorId": "sensor-001",
  "terminalId": "terminal-A",
  "name": "North Warehouse",
  "createdAt": "2026-11-05T08:00:00Z"
}
```

`sensorId` and `terminalId` are required, at most 100 characters long, and
accept only ASCII letters, digits, dots, underscores and hyphens. Identifiers
are case-sensitive. `name` is optional and at most 255 characters long.

Existing sensor identifiers return `409 SENSOR_ALREADY_EXISTS`; an occupied
terminal returns `409 TERMINAL_ALREADY_ASSIGNED` in the ordinary registration
flow. Concurrent registration remains a documented limitation; see the
[Sensor Domain decisions](docs/decisions/001-sensor-domain.md).

### Retrieve a sensor

```http
GET /api/sensors/sensor-001
```

Returns `200 OK` with the same sensor response shape, or a ProblemDetail
response with `404` and code `SENSOR_NOT_FOUND`.

### Assign or replace the current terminal

```http
PUT /api/sensors/sensor-001/terminal
Content-Type: application/json
```

```json
{
  "terminalId": "terminal-B"
}
```

Returns `200 OK` with the updated sensor. Assigning the same terminal again
also succeeds. The same terminal validation rules apply as for registration.

The operation preserves `sensorId`, `name` and `createdAt`, and does not
rewrite measurements already stored. It also supports historical sensors
whose current terminal is still `null`.

An unknown sensor returns `404 SENSOR_NOT_FOUND`. A terminal occupied by
another sensor returns `409 TERMINAL_ALREADY_ASSIGNED`, including the
tested case of two sensors concurrently claiming one available terminal.
Invalid request fields return `400 VALIDATION_FAILED`.

There is currently no API to remove an assignment or rename a sensor identifier.

## Create a Measurement

```http
POST /api/measurements
Content-Type: application/json
```

The example assumes that `sensor-001` is registered with `terminal-A`.

Example request:

```json
{
  "temperature": 23.5,
  "unit": "CELSIUS",
  "sensorId": "sensor-001",
  "terminalId": "terminal-A",
  "measuredAt": "2026-09-07T10:00:00Z"
}
```

Example response (`200 OK`):

```json
{
  "id": 1,
  "temperature": 23.5,
  "unit": "CELSIUS",
  "sensorId": "sensor-001",
  "terminalId": "terminal-A",
  "measuredAt": "2026-09-07T10:00:00Z"
}
```

Persistence-specific fields such as `createdAt` are deliberately not exposed
in measurement responses. Historical measurements may have `terminalId: null`;
new submissions must include a terminal identifier.

### Retries and quarantine

The history key is `(sensorId, measuredAt)`. An identical retry returns the
original measurement with `200 OK`, without adding a history row. Content is
compared using the numeric temperature value, unit and terminal identifier;
for example, `23.5` and `23.50` are equivalent.

A syntactically valid sample that cannot enter history is retained in quarantine.
It returns `200 OK` with a different response shape:

```json
{
  "status": "QUARANTINED",
  "reason": "UNKNOWN_SENSOR"
}
```

| Reason | Condition |
| --- | --- |
| `UNKNOWN_SENSOR` | The logical sensor is not registered. |
| `TERMINAL_NOT_ASSIGNED` | The registered sensor has no current terminal. |
| `TERMINAL_MISMATCH` | The submitted terminal differs from the current assignment. |
| `MEASUREMENT_CONFLICT` | History already contains a different sample for that sensor and instant. |

Identical historical retries are recognized before checking the current sensor
assignment. A different sample for an existing history key is quarantined as a
measurement conflict before registry checks.

Quarantine deduplication uses `sensorId`, `terminalId`, `measuredAt`,
`temperature` and `unit`. An exact retry reuses the existing quarantine entry,
preserving its reason and reception time, even if the registry has since changed.
An identical sample already in history takes precedence over a quarantine entry.
Clients must inspect the body: HTTP `200` alone does not distinguish accepted
history from quarantine.

Database constraints and recovery cover concurrent identical quarantine samples,
identical accepted measurements, and competing measurements with different content.
Quarantine review, correction, deletion and reprocessing APIs are deferred.

## Pagination and Sorting

Measurement queries support pagination and sorting.

### Pagination

```http
GET /api/measurements?page=0&size=25
```

Pagination defaults:

| Parameter | Default |
| --- | ---: |
| `page` | `0` |
| `size` | `50` |
| Maximum `size` | `1000` |

Pages are zero-based, so the first page is `0`.

Invalid pagination parameters result in `400 Bad Request`:

| Parameter | Invalid values | Application code |
| --- | --- | --- |
| `page` | Non-numeric or negative | `INVALID_PARAMETER` |
| `size` | Non-numeric, zero, or negative | `INVALID_PARAMETER` |
| `size` | Greater than `1000` | `PAGE_SIZE_TOO_LARGE` |

### Sorting

By default, measurements are ordered by:

1. `measuredAt` descending
2. `sensorId` ascending

This provides deterministic ordering when multiple measurements have the same timestamp.

Custom sorting can be specified using the `sort` parameter:

```http
GET /api/measurements?sort=measuredAt,asc
```

When only `measuredAt` is specified, `sensorId` is automatically added as a secondary sort criterion:

```text
measuredAt ASC, sensorId ASC
```

Similarly:

```http
GET /api/measurements?sort=sensorId,desc
```

uses `measuredAt` as the additional deterministic sort criterion.

Multiple sort criteria can be specified by repeating the `sort` parameter:

```http
GET /api/measurements?sort=sensorId,asc&sort=measuredAt,desc
```

Supported sort properties are:

- `measuredAt`
- `sensorId`

Unsupported sort properties result in `400 Bad Request`.

Pagination, sorting, and filters can be combined:

```http
GET /api/measurements?sensorId=sensor-001&page=0&size=25&sort=measuredAt,desc
```

A paginated response contains both the measurements and page metadata:

```json
{
  "content": [],
  "page": 0,
  "size": 25,
  "totalElements": 0,
  "totalPages": 0
}
```

## Filter by Sensor and Time Range

```http
GET /api/measurements?sensorId=sensor-001&from=2026-09-07T10:00:00Z&to=2026-09-07T12:00:00Z
```

A time range currently requires:

- `sensorId`
- `from`
- `to`

Incomplete or invalid combinations result in `400 Bad Request`.

Pagination and sorting remain available when querying a time range.

## Error Responses

Invalid requests use `application/problem+json` responses based on Spring's
`ProblemDetail` format. Every error response includes an HTTP `status` and an
application-level `code`. Responses with a specific reason also include
`detail`; validation failures include an `errors` array.

For example, an invalid pagination value:

```http
GET /api/measurements?page=-1
```

returns:

```json
{
  "status": 400,
  "detail": "Invalid value for parameter 'page'",
  "code": "INVALID_PARAMETER"
}
```

### POST validation errors

`POST /api/measurements` validates the required request fields:
`temperature`, `unit`, `sensorId`, `terminalId`, and `measuredAt`.

Missing or blank values return `VALIDATION_FAILED` with field-level errors:

```json
{
  "status": 400,
  "code": "VALIDATION_FAILED",
  "errors": [
    {
      "field": "sensorId",
      "message": "sensorId must not be blank"
    }
  ]
}
```

Malformed JSON, invalid enum values, or values that cannot be converted to
their expected type return `INVALID_REQUEST_BODY`.

### GET validation errors

`GET /api/measurements` returns the following application codes for invalid
query parameters:

| Code | When it is returned |
| --- | --- |
| `INVALID_PARAMETER` | A typed parameter is invalid, or `page`/`size` is not valid according to the pagination rules. |
| `PAGE_SIZE_TOO_LARGE` | `size` is greater than `1000`. |
| `SENSOR_ID_REQUIRED` | A time range is supplied without `sensorId`. |
| `INCOMPLETE_TIME_RANGE` | Only one of `from` and `to` is supplied. |
| `INVALID_TIME_RANGE` | `from` is after `to`. |
| `UNSUPPORTED_SORT_PROPERTY` | A sort property other than `measuredAt` or `sensorId` is requested. |

For example, a size above the limit returns:

```json
{
  "status": 400,
  "detail": "size must not be greater than 1000",
  "code": "PAGE_SIZE_TOO_LARGE"
}
```

# Testing Strategy

The project is developed incrementally following a TDD-oriented cycle:

```text
RED -> GREEN -> REFACTOR
```

The test suite deliberately separates different responsibilities.

### Service Tests

Service dependencies are mocked with Mockito.

These tests verify application behavior and interactions without accessing the real database.

### Controller Tests

Controller tests use MockMvc and mocked services to verify:

- HTTP status codes
- JSON contracts
- request validation
- query parameter handling
- service interactions
- pagination behavior
- default and custom sorting
- multi-field sorting
- invalid sorting requests

### Repository Integration Tests

Repository tests exercise the actual persistence layer and verify Spring Data JPA queries against PostgreSQL.

For example, repository integration tests verify that sensor and time-range filters return only the expected measurements.

Transactional tests are rolled back to keep tests isolated.

### Migration, service integration and concurrency tests

Migration tests create isolated schemas and verify upgrades from existing history,
including preservation of existing sensors and measurements. Service integration
tests flush and clear the persistence context before checking terminal changes
and unchanged measurement history.

Concurrency tests use real PostgreSQL transactions and barriers to force competing
requests past their initial lookup. These tests deliberately have no surrounding
test transaction and clean up their committed test records explicitly.

The M03 completion candidate passed **110 tests locally**. CI executes the suite
on pull requests targeting `master` and pushes to `master`.

### Application Context Test

The application context test verifies that the Spring Boot application can start with the expected configuration.

# Configuration

Runtime-specific configuration is externalized from the application.

The default configuration supports environment variables:

```properties
spring.datasource.url=jdbc:postgresql://${DB_HOST:localhost}:${DB_PORT:5432}/${DB_NAME:temperature}
spring.datasource.username=${DB_USERNAME:postgres}
spring.datasource.password=${DB_PASSWORD:}

server.port=${SERVER_PORT:8080}
```

Default values:

| Setting | Default |
| --- | --- |
| Database host | `localhost` |
| Database port | `5432` |
| Database name | `temperature` |
| Database user | `postgres` |
| HTTP port | `8080` |

Local development environments can override these values without modifying version-controlled configuration.

For example, a developer may use an untracked:

```text
application-local.properties
```

to configure local database credentials or non-standard ports.

Secrets and machine-specific configuration must not be committed to the repository.

# Database Migrations

Database schema evolution is managed using **Flyway**.

The migrations create and evolve the following structures:

| Version | Change |
| --- | --- |
| V1 | Measurement history and unique sensor/measurement-time key |
| V2 | Sensor registry with a unique current terminal |
| V3 | Backfill distinct sensor identifiers from existing history |
| V4 | Foreign key from accepted measurements to registered sensors |
| V5 | Nullable measurement terminal origin for compatibility with existing history |
| V6 | Independent quarantine storage without a sensor foreign key |
| V7 | Unique quarantine sample content |

Backfilled sensors have no inferred terminal or name. Historical measurements
retain `terminal_id = NULL`; no fictitious default terminal is introduced.
New API submissions require `terminalId`. Quarantine permits unknown sensors
without creating registry entries automatically.

Flyway owns schema evolution, while Hibernate/JPA maps the application model onto that schema.

# Running Locally

## Requirements

- Java 21+
- PostgreSQL
- Maven, or the included Maven Wrapper
- Docker, if PostgreSQL is run in a container

Start PostgreSQL using your preferred local setup.

Then start Temperature Monitor:

```bash
./mvnw spring-boot:run
```

If using a local Spring profile:

```bash
./mvnw spring-boot:run -Dspring-boot.run.profiles=local
```

Run the complete test suite with:

```bash
./mvnw test
```

## Local Configuration

Create your local configuration file from the provided template:

```bash
cp src/main/resources/application-local.example.properties \
   src/main/resources/application-local.properties
```
